# GaugeControl takes its geometry from the gauge

`GaugeControl` (`components/gauge/control.tsx`) used to take its own `min`, `max`, `startAngle`, `endAngle`, `orientation`, `length` and `wrap`, which had to match the gauge drawn inside it by hand, and it repeated the gauge's value-to-position mapping. Now the gauge is the only place that geometry is set. The catch is direction: the control wraps the gauge, and React context only flows down, so the control can't read the gauge's context, and it renders before the gauge does.

We considered:

- **The gauge registers its geometry with the control** through a context the control provides, in a layout effect. Pointer and key handlers would be fine, but the control's own markup needs the geometry too: `aria-valuemin`/`aria-valuemax`, `aria-orientation` and the `aspect-square rounded-full` versus `rounded-lg` box. Those would be missing from the server render and the first client render, then appear after hydration, which is a layout shift and goes against ADR 0002.
- **The control reads its child's props** (`Children.only(children).props`). It breaks as soon as the gauge sits inside a component of your own, as every smart home dial does.
- **The control owns the geometry** and the gauge reads it from the control. The values would live in one place, but on the wrong component: the drawing's own geometry would move to its input wrapper.

**Decision: the control hands its settings down, and the gauge root renders the slider.** `GaugeControl` renders no DOM. It puts its props (value, `onChange`, label, step, knob and the rest) in a context. `Gauge` and `LinearGauge` render `GaugeControlSurface` round their `<svg>`, inside their own gauge context. When a control is above, the surface renders the slider `div` and the hidden thumbs exactly as the control used to, but with the gauge's own `min`, `max`, `wrap`, `scale` and `positionOf`. With no control above, it renders the SVG alone. The markup is unchanged, and so are server rendering and hydration. ADR 0006 still holds: the control draws nothing of its own.

- **Only the outermost gauge is controlled.** `GaugeInset` and `LinearGaugeInset` don't render a surface, and the surface clears the control context for everything inside it. A gauge in a tooltip's content, for example, never becomes a second slider. Two sibling gauges inside one control would both become sliders, so a control wraps exactly one.
- **`min` and `max` stay on the control, as limits.** They default to the gauge's domain. When set, they bound the value the control will emit, and the pointer still maps onto the gauge's whole domain. A dimmer drawn from 0 that never goes below 1 (`LightDial` in `smart-home-dashboard.tsx`) needs this. Before, its control's `min={1}` also skewed the pointer mapping by 1%.
- **Rotation follows.** The pointer now maps onto the gauge's scale as drawn, including `rotate`. Before, the control used the unrotated angles it was given.
- **`GaugeTooltip` finds its owner through context.** The surface provides its element (`useGaugeControlElement`). The tooltip listens there for focus, which covers a range control whose group isn't focusable but whose thumbs are. Without a control it falls back to the nearest natively focusable ancestor, such as a button round the gauge. The hard-coded `[data-slot="gauge-control"]` selector is gone. `data-slot` stays on the element for styling.
